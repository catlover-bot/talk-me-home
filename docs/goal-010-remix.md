## Dispatch identity and local history

R1 codes pin a resolved catalog profile, certified starting orientation, one assignment and a presentation nonce. The syntax is `R1-PP-SS-A-NNNNNNNN-CCCCCCCC`: two base-36 selection fields, assignment digit, eight hexadecimal nonce characters and an eight-character SHA-256 checksum. R1 freezes catalog order, starting tables and rule meaning; unsupported versions and malformed selections reject. The checksum catches mistakes and is not a security credential. Codes are public replay references, never session ownership, inspection permission or saved progress.

New dispatch uses server entropy and samples a mechanical family before its installed-row variants. It considers at most the last twelve local dispatch codes, excludes those base families while alternatives remain, and otherwise excludes the immediately preceding family. It prefers changing at least two of panel, procedure and corridor arrangement where the eligible pool permits. A bounded thirteen-candidate nonce check avoids exact recent codes even under repeated entropy. Corrupt history entries are ignored; oversized or object-valued submissions reject without a search. No performance, errors or speech recognition affect selection.

Daily uses the server's UTC date and frozen R1 catalog. Its core rescue assignment is fixed for all players; recent history does not affect it. The date and code are pinned at Start. A daily code can later be replayed, reproducing initial conditions with fresh ownership scope, round/visit/proposal identifiers and no old progress. Replay reproduces neither AI wording nor player choices. Restarting the server still loses active missions.

The local diary is bounded convenience data. It stores dispatch references and labelled outcomes, not speech, transcripts or cloud progress. Clearing or blocking storage does not prevent play. Same conditions and Other approach return deliberately to setup with a replay code; Other approach is a private intention.
